## D06：已确认本地校验误拦截

学生代码共 3 行：

```python
n = int(input())
for i in range(1, n + 2):
    print(i)
```

公开输入 `3`：预期输出 1、2、3，实际输出 1、2、3、4，共 4 行。公开输入 `0`：预期不输出字符，实际输出 1。

候选诊断正确指出循环上界多了 1。触发拒绝的证据解释原文是：

> n=3 时 range(1, n+2)=range(1,5)，除正确的 1、2、3 外多产生 4，形成第 4 行错误输出。

验收轨迹依次为：`provider_response → diagnosis_parse → diagnosis_grounding → diagnosis_quality → unsupported_claim → invalid_response`。没有进入 `diagnosis_review`，因此本次不是第二次模型审核判错。

程序位置：`backend/app/services/hint_quality.py` 的 `quality_issues()`。当前正则从解释中提取所有“第 N 行”，直接与 `len(code.splitlines())` 比较，没有区分源码行和输出行。这里 N=4、源码行数=3，因此拒绝了一段与公开执行结果一致的解释。

离线对照使用同一份候选，只将证据解释中的“第 4 行”改称“额外一行”，其他内容和程序规则均不变：本地质量检查从 `['unsupported_claim']` 变为 `[]`。这证明了误拦截的触发条件；不代表修改后的候选已通过真实模型审核。

**性质与建议：**这是需要修补的程序校验缺陷，会影响反馈可用性；本次没有影响判题正确性。应区分源码位置与输出位置，并保留对虚构源码行号的检查，补充“3 行源码产生第 4 行输出”等回归用例。

## D07：小测解释违反引导约束

学生代码：

```python
n = int(input())
total = 0
for i in range(1, n + 1):
    total = i
print(total)
```

公开输入 `4`：预期为 10，实际为 4。程序每轮用当前数字覆盖 `total`，未保留此前累积值。由于部分测试通过，系统正确选择学习引导分支，不生成疑似误区诊断标签。

候选主提示：

> 你的循环确实遍历了 1 到 n，但请逐轮观察 total 的变化：每轮结束后，total 里保存的是前面所有数的和，还是变成了某个单个数？想一想累加器变量在每次迭代时该如何更新。

候选概念小测询问累加器应如何更新，正确选项为“把当前元素加到累加器已有的值上，并保存回累加器”。小测解释原文：

> 累加器的含义是“已经积累的和”。每轮应把当前元素叠加到已积累的值上并写回同一变量（如 total = total + i），若用当前元素直接替换，旧的和就丢失了，最终只剩最后一个元素。

验收轨迹依次为：`provider_response → guidance_parse → guidance_knowledge → guidance_private_evidence_or_code → guidance_replacement_statements → invalid_response`。具体拒绝理由为 `Guidance must not contain replacement statements`。

程序位置：`backend/app/services/error_analysis.py` 的 `_generate_guidance()`。它对主提示、小测题干、选项和作答后解释统一检查替换语句。小测解释中的 `total = total + i` 正好是这道题的直接修正写法，因此触发拒绝；主提示本身没有触发该规则。

离线对照将候选小测解释中的“（如 total = total + i）”删除，其他字段和程序规则均不变，通过同一引导流程回放：原候选 `invalid_response`，删除赋值示例后 `ready`。回放使用保存正文和模拟模型返回，不产生真实模型调用，也不计为真实复测成功。

**性质与建议：**这次拦截符合现有“引导不提供直接修正代码”的规则，尚无证据证明此处是正则误判。可确认的是模型生成与产品限制不一致，且一个小测解释导致整份提示不可展示。优先明确提示词对所有小测字段均禁止修正语句，并补充该类候选的回归测试；若后续考虑舍弃不合格小测、保留主提示，应单独定义并验证该行为。
