# Ottly 参赛文档写作工作区

当前目标：2026-10-30 提交，评审通过 Docker 本机运行包体验。正文初稿原始写作基线为 `921fd5d`；当前正式 AI 验收基线见[版本冻结记录](freeze-2026-10-28/冻结版本.md)，标签为 `acceptance-baseline-2026-10-28`。最终报告需与实际验收及发布版本对应。

先阅读[技术方案初稿](technical-proposal-draft.md)。它已经按照官网六部分参考大纲写入当前产品事实、架构图、反馈流程与案例脚本；【待补】表示尚无足够材料支撑，不能当成最终结论。

## 1. 材料分工

| 材料 | 回答的问题 | 本项目写作重点 |
| --- | --- | --- |
| 主技术方案 | 为什么做、怎样实现、有何价值、证据是什么 | 以完整学习过程解释证据反馈、差异化引导、改对后加练和执行回放 |
| 软件使用与部署说明 | 评审拿到包后怎样启动和体验 | 环境、源码/镜像启动、模型配置、演示路线、停止重启和故障处理 |
| 核心算法说明 | 团队具体设计了哪些处理规则 | 证据筛选、输出差异、结构与内容校验、反馈路由、候选排序、生成题验证；给出输入、步骤、输出与失败分支 |
| 测试报告 | 哪个版本在什么条件下通过了什么 | 软件回归、真实模型语义质量、耗时成本、人工复核、干净环境部署及未解决问题 |
| 演示脚本和答辩材料 | 评审如何在几分钟内理解作品 | 统一使用同一代表案例，说明真实等待与剪辑，结果对应测试报告 |
| 佐证与运行包 | 正文结论如何核对和复现 | 脱敏记录、可核对的反馈、依赖来源、代码与镜像版本等 |

主技术方案概述核心算法、测试与部署；其他文档提供详细内容，避免每份材料重复粘贴全部说明。官方提交槽位、模板及是否合并附件，以报名系统和所属赛区实际要求为准。

## 2. 建议的正文篇幅

建议正文约 12～16 页，作为团队写作目标，不是官方页数限制。产品定位约 1～2 页，架构与创新约 3 页，核心流程和案例约 3 页，测试部署约 3～4 页，价值局限约 1～2 页，附录按必要内容补充。官方模板中的必填项优先。

一段技术说明采用“遇到的问题 → 当前处理机制 → 实际例子 → 测试依据”的顺序。先交代可观察的行为，再给关键实现；避免逐个罗列 API 或把提交日志当研发总结。

建议至少准备四张图：系统架构、判题至反馈流程、改对至推荐流程，以及真实案例的执行回放。初稿已有前两张草图，定稿前根据官方模板统一字体、配色和图注。

## 3. 必须统一的表述

| 主题 | 当前可用表述 | 需要额外证据才能使用的说法 |
| --- | --- | --- |
| 模型 | 调用 DeepSeek API；团队实现应用流程与约束 | 自研或训练了当前底座模型 |
| 误区 | 依据公开执行证据生成疑似标签，证据不足保留 other | 准确测量学生认知、已经识别全部薄弱点 |
| 适应性 | 根据错误记录、知识点和候选题安排练习；当前目标难度固定 | 完整知识追踪、持续自动调整难度 |
| 回放 | 真实轨迹驱动，展示规则人工设计，模型按需讲解 | AI 自动为任意 Python 生成可视化 |
| 测试 | 软件自动测试与真实模型人工复核分别报告 | 接口成功率等于诊断正确率 |
| 学习价值 | 当前实现支持理解执行与巩固练习 | 无真实研究数据的学习效率提升百分比 |
| 部署 | 本机 Docker 软件，AI 功能需要网络与模型密钥 | 全功能离线运行、已验证可安全公开部署 |
