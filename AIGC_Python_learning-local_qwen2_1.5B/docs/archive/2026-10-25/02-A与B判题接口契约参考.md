## 2. 当前 HTTP 契约

### 2.1 正式提交

`POST /api/v1/code/submit`

请求头：`Content-Type: application/json`、`Authorization: Bearer <access_token>`。

```json
{
  "problem_id": "level2",
  "code": "total = 0\nfor i in range(1, 101):\n    total = i\nprint(total)"
}
```

| 字段 | 类型 | 当前规则 |
|---|---|---|
| problem_id | string | 必填；目前题库只有 level1、level2 |
| code | string | 必填，1–6000 字符，不能全为空白；保留原始缩进和换行 |

请求模型禁止额外字段。当前发送 `request_id`、`submission_id`、`problem_version`、`expected_output`、`timeout` 或 `user_id` 均不符合正式提交请求模型。客户端不能指定测试或答案。

### 2.2 返回结构

以下为与当前模型一致的示例，AI 文本和 execution_time 不保证每次相同：

```json
{
  "code": 200,
  "data": {
    "problem_id": "level2",
    "judge": {
      "status": "wrong_answer",
      "passed": false,
      "passed_cases": 0,
      "total_cases": 1,
      "cases": [
        {
          "case_id": "stdout-1",
          "passed": false,
          "expected_output": "5050",
          "actual_output": "100\n",
          "output_available": true,
          "errors": [],
          "execution_time": 0.001
        }
      ]
    },
    "analysis": {
      "status": "ready",
      "message": "以下为基于本次测试证据的 AI 提示。",
      "model": "qwen2.5-coder:3b-instruct",
      "content": {
        "suspected_cause": "疑似每次循环覆盖了累计结果。",
        "evidence": [
          {
            "case_id": "stdout-1",
            "field": "actual_output",
            "quote": "100",
            "explanation": "程序输出了循环的最后一个数，和要求的总和不同。"
          }
        ],
        "knowledge_points": ["累加器", "赋值与累加"],
        "hints": {
          "level1": "总数需要保留哪些已经算过的值？",
          "level2": "观察循环内的赋值会不会覆盖上一轮累计的结果。",
          "level3": "用前两轮在纸上核算，检查新总数是否包含旧总数。"
        }
      }
    }
  }
}
```

提交响应顶层只有 `code` 和 `data`，**不保证有 msg**。题目、判题和分析都在 data 内。没有 submission_id、时间戳、进度或推荐字段。

### 2.3 HTTP 错误

| HTTP | 当前含义 | 响应形态 |
|---|---|---|
| 200 | 已返回判题及分析状态，学生不一定通过 | 上述 code/data 结构 |
| 401 | 无令牌、令牌失效、使用刷新令牌、用户不存在或被禁用 | detail 字符串 |
| 404 | problem_id 不在题库 | detail 字符串 |
| 422 | 请求缺字段、字段类型不符、空白/过长代码或额外字段 | FastAPI 验证错误 detail 数组 |

```json
{"detail": "题目不存在"}
```

不要按旧草案要求所有错误都包装成 code/msg/data。非预期服务异常仍可能产生 5xx，当前没有统一业务错误对象。已知执行器故障会被包装进 judge，而不是自动变成 HTTP 503，详见第 6 节。

### 2.4 试运行

现有 `POST /api/v1/code/run` 同样要求登录，请求为 code 和可选 timeout。code 最多 20000 字符；timeout 默认 10 秒、范围 1–10 秒，当前前端传 3 秒。其响应为 `code / msg / data`，data 包含 success、output、output_available、errors、execution_time。

试运行不调用教学分析。前端正式提交无需先运行，不使用旧运行结果决定通过。

## 3. A 的交付：Problem → JudgeResult

### 3.1 当前题库模型

```text
Problem:
  problem_id: string
  title: string
  description: string
  tests: TestCase[]

TestCase:
  case_id: string
  expected_output: string
```

| 题目 ID | 题意 | 当前测试 |
|---|---|---|
| level1 | 输出 Hello, World!，没有输入 | stdout-1，预期 Hello, World! |
| level2 | 使用 for 计算 1 到 100 的和，没有输入 | stdout-1，预期 5050 |

当前没有测试输入、公开/隐藏标记、题目版本、固定知识点 ID 或教学约束字段。case_id 在不同题目之间可以重复，关联时须结合 problem_id。

判题函数已经循环处理 tests，但两题目前各只有一个无输入测试。它只比较输出，不检查是否使用 for，所以 `print(5050)` 目前会通过第二关。不能把“支持 tests 数组”写成“已具备多输入判题”。

### 3.2 JudgeResult 字段

| 字段 | 类型 | 当前含义 |
|---|---|---|
| status | string 枚举 | accepted / wrong_answer / execution_error / timeout |
| passed | boolean | 是否所有用例通过，前端据此显示通关 |
| passed_cases | integer | cases 中 passed=true 的数量 |
| total_cases | integer | 本题 tests 数量 |
| cases | CaseResult[] | 每个测试的完整结果，按题库顺序 |

每个 CaseResult：

| 字段 | 类型 | 当前含义 |
|---|---|---|
| case_id | string | 对应测试标识 |
| passed | boolean | 执行成功且输出比较相等 |
| expected_output | string | 标准输出 |
| actual_output | string | 已捕获输出，可能为空或异常前的部分输出 |
| output_available | boolean | 输出是否已成功采集，默认 true |
| errors | ExecutionError[] | 无错误为 [] |
| execution_time | number | 秒；不要当作精确性能基准 |

ExecutionError 包含 `type: string`、`line: integer|null`、`message: string`。line 指向学生代码行号，无法定位时为 null；不包含旧草案的 column、case_id 字段，case_id 位于所属 CaseResult。

状态计算：

1. 执行成功且 `actual_output.strip() == expected_output.strip()`，该用例通过。
2. 全部用例通过则 accepted，否则先判 wrong_answer。
3. 任一失败用例含 type 为“超时警告”的错误，则总体 timeout。
4. 无超时，但失败用例存在 errors，则总体 execution_error。

因此当前语法错误、运行异常、禁止操作、输出超限和执行器故障可能统一落到 execution_error，进一步类型看 cases[].errors[].type。不能直接把未实现的 syntax_error、runtime_error、system_error 等当作 judge.status。

当前比较会忽略两端所有空白，与 v0.1 建议的“只忽略一个末尾换行”不同。修改比较规则会改变通过标准，须同步题目和测试。

输出含义必须区分：

- `actual_output=""` 且 `output_available=true`：确实采集到了空输出。
- `actual_output=""` 且 `output_available=false`：输出未采集，不能推断程序没有输出。
- 普通运行异常可以保留异常前的部分输出；有异常时即使输出等于答案也不通过。

### 3.3 执行器已有能力

每个用例使用独立子进程；正式提交每例固定 3 秒，超时终止该执行进程。stdout 和 stderr 分别通过 LimitedStringIO 限制为 8000 字符，超限通过 OutputLimitError 报告。此处并非所有资源的统一限制，也未实现内存限额。

这已经改善卡死和输出串扰，但不是恶意代码的操作系统级隔离环境。受控输入、内存限制和更强隔离属于后续工作。

## 4. B 的交付：Problem + code + JudgeResult → AnalysisResult

后端边界直接沿用：

```python
judge = judge_submission(problem, code)
analysis = await analyze_failure(problem, code, judge)
```

A 提供本次题目、原始代码和真实判题证据；B 根据证据生成讲解，不改判题、标准答案或通过状态。

### 4.1 分析外层

| 字段 | 类型 | 当前含义 |
|---|---|---|
| status | string 枚举 | ready / skipped / unavailable / timeout / invalid_response |
| message | string | 可展示的状态说明，不用于程序分类 |
| model | string 或 null | 实际配置的模型名，不能固定依赖某个模型 |
| content | AnalysisContent 或 null | 仅 ready 时有有效内容 |

| status | 触发与前端行为 |
|---|---|
| ready | 分析通过校验，允许逐级展示提示 |
| skipped | judge.passed=true，未调用模型，content=null |
| unavailable | 模型未配置/HTTP 请求失败，或执行器 RunnerError；显示 message |
| timeout | 分析超出等待期限；显示 message |
| invalid_response | 证据不可用/上下文过长，或模型输出在重试后仍未通过校验；显示 message |

正确提交时 analysis 不是 null，而是：

```json
{
  "status": "skipped",
  "message": "测试已通过，无需 AI 分析。",
  "model": null,
  "content": null
}
```

目前 AI 分析总等待预算为 90 秒；模型内容校验失败可在同一预算内重新生成一次，总计最多两次模型请求。前端提交请求期限为 180 秒。未来增加用例时需重新核对总判题时长与前端期限。

### 4.2 AnalysisContent

| 字段 | 类型与数量 | 当前语义 |
|---|---|---|
| suspected_cause | string | 自然语言疑似原因，不是统一分类代码 |
| evidence | Evidence[]，1–3 项 | 本次失败用例的证据引用 |
| knowledge_points | string[]，1–4 项 | 模型生成的知识点文本，不是固定题库字典 |
| hints | object | level1、level2、level3 三个字符串 |

Evidence：

```json
{
  "case_id": "stdout-1",
  "field": "actual_output",
  "quote": "100",
  "explanation": "实际输出为最后一个数，提示需要检查累加操作。"
}
```

field 只能是 actual_output 或 error_message。B 使用 evidence_options 从失败用例生成允许引用的三元组 case_id/field/quote：

- 有 errors 时引用错误 message。
- 无 errors 且 output_available=true 时引用 actual_output。
- 引用文本按 `原文.strip()[:1000].strip()` 处理，quote 最大 1000 字符。
- 校验时三元组必须完整匹配允许证据，不允许编造引用；通过用例不作为这里的失败证据。

讲解字段限制长度与部分符号，level1 必须以问号结尾，三个提示不能完全相同。内层模型拒绝额外字段。当前这些检查不能保证因果解释正确、知识点归类准确、提示逐级深入，也没有机械校验讲解中的所有行号。

目前没有稳定的 suspected_cause_id、UNKNOWN 枚举、置信度或 countable 字段。不能直接依赖自由文本统计“同类误区次数”。

### 4.3 前端约定

前端依据 judge.passed 判断是否通过；仅当 analysis.status=ready 时读取 content。三级提示初始均隐藏，由学生逐级展开；展开不发起新的 AI 请求。

修改代码或重新提交会清除旧分析。提交期间编辑器只读，并阻止本页面再次运行或提交；这不是后端幂等保证。

## 5. 建议两人现在固定的兼容规则

1. 保留 /code/submit、problem_id、judge、analysis 及其现有字段，不为旧草案重命名。
2. A 保证判题来源于本次代码与服务端题库，保持 passed、status、计数一致。
3. B 保证仅用本次失败证据，成功提交不请求模型，分析失败不改判题结论。
4. 前端只按枚举状态处理，不解析中文 message 推断错误类别。
5. 修改状态枚举、提示结构、证据格式或公开结果结构时，同时更新 Pydantic 模型、前端、B 的证据处理、测试与本文。
6. 请求模型 extra=forbid，新增请求字段也需要先修改后端；不能假定加字段天然兼容。

这些是建议固定的协作规则，不表示两人已经正式确认了所有未来扩展。

## 6. 当前限制必须写进契约

| 现状 | 实际影响 |
|---|---|
| 没有提交持久化及 submission_id | 无法按提交 ID 恢复结果，也未形成错题历史 |
| 返回文案写“判题结果已保留” | 目前只表示本次响应仍带 judge，不代表写入数据库 |
| 没有 request_id 和后端去重 | 重复 HTTP 请求会重新判题，也可能重新请求模型 |
| 没有题目版本和后端主线解锁校验 | 登录成功不等于实现了关卡权限；静态地图不是持久化进度 |
| AI 失败时 content=null | 尚无固定三级备用提示或规则优先提示 |
| 当前所有 cases 返回前端，失败 cases 原样进入模型上下文 | 尚无隐藏用例保护，不能直接加入隐藏测试投入使用 |
| RunnerError 归入 execution_error | 将来统计学习失败时须识别并排除系统故障，不能全部计学生答错 |
| 题库模型未限制 tests 非空 | 空测试集会因 0==0 被判通过；新增题目必须保证至少一例，并建议补模型校验 |
| 单一固定输出，无 for 约束 | 接受写死答案属于当前判题能力边界 |

## 7. 下一阶段怎样扩展（建议，未实现）

按实际功能逐步补字段，不一次引入远期草案的全部接口。

| 优先事项 | A 的工作 | B/前端需同步的内容 |
|---|---|---|
| 多输入判题 | 先确认题面；为 TestCase 增加受控输入，执行器逐例注入；补普通及边界测试 | AI 上下文、证据格式与页面支持输入信息；保留现有输出字段名 |
| 明确错误分类 | 建议保留四个 status，先新增稳定的 error_code 区分语法/运行/禁止操作/资源/系统故障 | 用稳定代码分类，系统故障不计学习失败；字段位置和枚举实施前共同定 |
| 固定知识点与错因字典 | 为题目提供审核过的 knowledge_ids 和目标错因 | 在 analysis.content 中增设稳定错因 ID，保留 suspected_cause 作解释；允许 UNKNOWN |
| AI 回退 | 提供题目及知识点基础资料 | B 准备审核过的三级备用提示；共同决定来源字段及状态兼容方式 |
| 隐藏用例 | 为题库增加 visibility，区分后端完整结果和公开结果 | B 只能把公开证据传模型；前端不依赖 cases.length 等于 total_cases |
| 提交记录 | 提供题目版本、代码快照和完整判题数据 | 保存记录并生成 submission_id；再设计查询、去重和错题页 |

采用隐藏用例前，必须同时完成对 case 列表、实际输出、错误信息、AI 引用的过滤。保留总通过数和总用例数；隐藏输入、答案、输出、宿主路径和原始异常栈不能通过讲解泄漏。当前代码没有这层转换，不应在文档中宣称“已脱敏”。

如果决定把第二关改为输入 n 求和，这是题目行为与输入能力的变更。先确认题面和 for 约束，再实现；对固定题面重复运行四次不能解决写死答案问题。

## 8. 联调验收与本次核对范围

| 场景 | 当前应观察到 |
|---|---|
| 正确求和代码 | judge.accepted、passed=true；analysis.skipped、content=null；模型调用为 0 |
| 累加写成覆盖赋值 | wrong_answer，actual_output 为 100 加换行，预期 5050 |
| range 少算终点 | wrong_answer，actual_output 为 4950 加换行 |
| 缺冒号 | execution_error，errors 包含“语法错误”及行号 |
| 未定义变量 | execution_error，errors 包含 NameError |
| 死循环 | timeout、output_available=false；执行进程终止，后续运行正常 |
| 模型不可用/超时/非法证据 | 保持 judge；analysis 为对应失败状态，content=null |
| 未登录、未知题目、请求加答案字段 | 分别为 401、404、422 |
| 第二关直接打印 5050 | 当前 accepted；这是能力边界，不是防作弊验收通过 |

核对来源为当前 Pydantic 模型、API 路由、服务调用、前端消费代码及现有测试。docs/live-submission.json 是仓库保存的历史模型响应，不代表本次重新调用了模型或全部讲解质量合格。

本次本机验证：执行器及不依赖 HTTP 测试夹具的相关测试共 11 项通过；20 项 HTTP 提交测试在初始化时受环境问题阻止。改用独立临时目录后确认当前 Python 缺少 argon2 依赖，未完成 HTTP 回归；本次未启动真实模型。本稿不声称全链路运行验收通过。
