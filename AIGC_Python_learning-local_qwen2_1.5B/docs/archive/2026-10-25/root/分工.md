# 两人开发分工与接口约定

> 目标：先把「提交代码 → 判题 → AI 三级提示 → 保存错题」做稳，再增加针对性加练。现在不做 AI 自由出题，也不训练误区模型。

## 1. 先一起定好判题结果格式

A 负责生成判题结果，B 负责拿结果给 AI 分析、存错题记录。**已有接口能用就尽量沿用，不用为了下面的例子重写整套接口。** 建议统一为：

```json
{
  "question_id": "Q006",
  "submission_id": "S001",
  "passed": false,
  "error_type": "wrong_answer",
  "tests": [
    {"input": {"n": 5}, "passed": true, "expected": 15, "actual": 15},
    {"input": {"n": 100}, "passed": false, "expected": 5050, "actual": 4950}
  ],
  "error_message": null
}
```

- `passed`：是否全部通过；`error_type`：判题失败类型，建议约定 `syntax_error` / `runtime_error` / `timeout` / `wrong_answer`，通过时为 `null`。
- `tests`：每个测试用例的输入、是否通过、预期和实际结果；报错或超时时，`actual` 可以为 `null`，详细信息放在 `error_message`。
- **注意区分**：`error_type` 是程序判出来的错误类型；AI 说的“疑似循环边界问题”等是另一回事，单独保存在 AI 分析或错题记录里。
- 隐藏用例不要把全部输入和答案直接发给学生端；后端可保留完整结果，前端只显示允许公开的部分。学生代码由提交接口单独传递或按 `submission_id` 读取，不必塞进每条判题结果。

## 2. A：负责判题和题库（让系统判得准）

- 把目前每题一个测试用例改成**多用例**，优先检查写死答案也能过关的问题。
- 整理 12 关的知识点、测试数据；区分语法错误、运行异常、超时、结果错误。
- 后面准备少量已经验证过的加练题，标注它们练哪个知识点。
- **要和 B 商量**：判题接口返回哪些字段、哪些失败证据可以交给 AI、前端能展示哪些测试信息。

## 3. B：负责 AI 提示和学习记录（让系统教得好）

- 优化 Qwen 的三级提示：不要重复、别太早说出答案、别乱猜；失败时使用备用提示。
- 让 AI 额外返回一个**统一的疑似错误标签**（如 `range_boundary`、`accumulation_error`、`other`），并保留不确定的情况。
- 保存学生的题目、提交结果、疑似错误标签、提示使用情况，做一个简单的错题记录页面。
- **要和 A 商量**：哪些测试失败信息可以拿到、12 关对应哪些知识点、哪些加练题可以用于后续推荐。

## 4. 两人需要一起确认的三件事

1. **接口**：先拿一份真实提交结果对照第 1 节，敲定字段名、类型和失败时的返回方式，避免各写各的。
2. **标签**：先定 5 个左右常见疑似误区标签；判题报错类型和 AI 推断标签不要混用。
3. **加练规则**：先从已验证题库推荐；同一道题反复提交不要简单当成多次独立误区。加练不拦主线，复习建议也不强制。

## 5. 按这个顺序做，最后一起验收

- **第一轮（同时做）**：A 完成多用例判题；B 优化三级提示、统一错误标签。
- **第二轮（同时做）**：A 整理 12 关及少量加练题；B 完成错题入库和页面。
- **第三轮（一起联调）**：把历史错误与题目知识点关联，先实现简单的加练推荐。

**验收就看一条流程**：学生提交错误代码 → 判题指出真实失败用例 → AI 给出合理的分级提示 → 错题被保存 → 再犯类似错误时可以看到对应的巩固建议。正确提交则直接通过，不调用 AI。
