# 第二阶段第一步：个人提交与错题历史

## 范围与验收

只实现提交持久化、提示级别记录和个人历史查询/页面。复用现有账号、题目、判题器、AI 分析和三级提示。暂不加入误区标签、跨题统计或加练推荐，也不改变 `judge` 格式。

验收：错误、正确及 AI 不可用的提交都保存；重新登录仍可查询；一个用户不能读取或更新另一个用户的记录；提示最高已看级别只能上升；后续同题正确提交不覆盖旧错误，旧记录可显示“后来已通过”。

## 数据与接口

新增 `learning_submissions` 表，与 `users.id` 关联。每行保存一次提交：`problem_id`、题目标题/描述快照、学生代码、判题 JSON、AI 分析 JSON、是否通过、程序错误类型、最高已看提示级别和创建时间。普通聊天表保持原用途。题目 ID 当作不透明字符串；A 以后更名时只在接口入口映射，旧题目快照仍可展示。

原提交响应只增加 `submission_id`。新增本人记录列表（可筛选错误、分页）和提示查看级别更新接口。服务端从登录态取 `user_id`，不接受客户端传入用户 ID。先保存判题，再调用 AI 并补上分析；模型故障仍有判题记录。

前端增加“我的错题”入口，默认筛选失败记录、可切换全部提交；复用原三级提示组件展示历史记录。点击新一级时同步记录，失败时显示未同步提示。正确尝试单独保留，旧错题根据后续同题正确提交标记“后来已通过”。

## 实施顺序

1. 写后端失败测试：持久化、重新登录、跨用户隔离、提示单调更新、AI 不可用及后续通过。
2. 增加一张表和最小 API；运行后端回归。
3. 写前端失败测试：历史请求鉴权与提示点击同步；增加页面、路由和入口。
4. 运行前端测试/构建、后端全部测试；用临时数据库做真实 HTTP 验收。Docker 未运行时不宣称容器验收。

## 手动检查步骤

1. 按项目现有启动方式启动数据库、后端与前端，登录学生账号 A。
2. 进入第 2 关，提交 `total = 0\nfor i in range(1, 101):\n    total = i\nprint(total)`（输入时分四行）；查看第 1、2 级提示。
3. 打开侧栏“我的错题”，展开该记录；应看到提交代码、实际输出 `100`、以及已看的两级提示。刷新或重新登录后再次检查。
4. 把赋值改为 `total += i` 再提交；切换“全部提交”应同时看到通过与未通过的两次尝试，旧错题标为“后续已通过”。
5. 登录账号 B；“我的错题”不应出现账号 A 的记录。
