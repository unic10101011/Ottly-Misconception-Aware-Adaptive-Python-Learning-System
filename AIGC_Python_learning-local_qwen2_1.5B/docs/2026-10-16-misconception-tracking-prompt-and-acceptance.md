# “疑似误区追踪”开发提示词与验收要求

## 一、开发提示词

请在当前项目已有的“程序判题 → AI 错误分析 → 三级提示 → 提交记录 → 错题复习”流程上，实现第一版“疑似误区追踪”。

开始修改前，请先阅读并复用以下现有代码：

- 提交和判题接口
- Qwen 错误分析及输出校验
- `LearningSubmission` 提交记录
- `analysis_json` 分析结果
- 错题列表和复习记录
- 用户身份及数据隔离逻辑
- 当前工作区中的未提交修改

不要重新开发判题器，不要覆盖无关修改。

### 1. 功能目标

学生提交错误代码后，系统在已有 AI 分析结果中增加统一字段：

```json
{
  "misconception_tag": "range_boundary"
}
```

这个字段表示“根据本次题目、学生代码和真实判题证据推测的疑似知识误区”。

它只是本次提交的分析结论，不代表学生永久没有掌握这个知识点。

### 2. 固定标签

第一版只能使用以下标签：

```text
range_boundary
accumulation_error
condition_error
variable_error
syntax_error
other
```

含义如下：

| 标签 | 含义 |
|---|---|
| `range_boundary` | 循环范围、起点、终点或是否包含边界的问题 |
| `accumulation_error` | 累加变量初始化、更新或覆盖问题 |
| `condition_error` | `if`、循环条件或布尔判断问题 |
| `variable_error` | 变量未定义、用错变量或变量值使用错误 |
| `syntax_error` | 已有判题证据确认的语法或缩进错误 |
| `other` | 证据不足、无法可靠分类或暂未覆盖的其他问题 |

模型不能自由创造新标签。使用 Pydantic、枚举或等效方式严格校验。

如果模型返回不在列表中的标签，不能直接保存，应进行一次必要的修正或降级为 `other`。

### 3. 证据要求

误区标签必须根据以下内容产生：

- 题目要求
- 学生代码
- 程序判题结果
- 失败测试证据
- 已公开的运行错误

不得根据变量名、代码风格或主观猜测生成误区。

例如：

- `range(1, 100)` 导致少计算 100，且失败输出能支持该结论，可以标记 `range_boundary`。
- 循环中写成 `total = i`，判题结果和代码能支持累加值被覆盖，可以标记 `accumulation_error`。
- 编译器明确报告缺少冒号，可以标记 `syntax_error`。
- 仅看到输出错误，但不能判断具体原因，应标记 `other`。
- 不能因为变量名叫 `sum`，就推断存在变量命名错误。

语法错误可以直接根据程序判题证据确定为 `syntax_error`，不必调用模型猜测。

`error_type` 和 `misconception_tag` 必须保持区别：

- `error_type`：程序确定的实际错误类型，例如语法错误、超时或输出错误。
- `misconception_tag`：根据证据推测的学习误区。

### 4. 保存规则

优先复用现有 `LearningSubmission.analysis_json`，不要为了第一版新建复杂误区数据库或知识库。

AI 分析成功时，结果中必须包含：

```json
{
  "status": "ready",
  "content": {
    "misconception_tag": "range_boundary",
    "suspected_cause": "...",
    "evidence": [],
    "knowledge_points": [],
    "hints": []
  }
}
```

规则如下：

- 判题通过时不生成误区标签，也不调用 AI。
- 模型不可用、超时或解析失败时，不得编造误区。
- 分析未成功时，`misconception_tag` 使用 `null`，并且不进入误区统计。
- `other` 只表示分析成功但无法进一步可靠分类，不能用来代替模型故障。
- 保存提交当时的标签，后续提示词或模型变化不能自动改写历史记录。
- 不得保存隐藏测试的输入、期望输出或其他敏感内容。

### 5. 个人误区统计

增加一个只查询当前登录用户的误区统计接口，或者在不破坏现有接口的前提下扩展学习记录接口。

建议使用独立接口：

```http
GET /api/v1/code/misconceptions
```

建议返回：

```json
{
  "code": 200,
  "data": {
    "items": [
      {
        "misconception_tag": "range_boundary",
        "label": "循环边界",
        "occurrence_count": 3,
        "problem_count": 2,
        "latest_at": "2026-10-16T08:00:00Z",
        "later_passed_count": 1
      }
    ]
  }
}
```

统计要求：

- 只能统计当前用户。
- 只统计判题失败且分析成功的记录。
- 同一标签在不同题目中重复出现时能够累计。
- 同一道题多次提交错误也保留真实次数。
- 后续做对不能删除以前的错误记录。
- 需要保留“后来做对”的信息，不能因为犯过一次错误就认定一直没有掌握。
- 不同用户的数据必须完全隔离。
- 所有统计依据保存的数据计算，不能每次查询时重新调用 AI。

### 6. 前端展示

在个人错题或学习记录页面增加简洁的“疑似误区概览”。

至少显示：

- 误区中文名称
- 出现次数
- 涉及题目数量
- 最近出现时间
- 后来做对的数量

页面文字应明确写“疑似误区”或“根据提交记录推测”，不要显示成确定诊断。

没有有效记录时显示正常空状态，例如：

> 完成一些题目后，这里会根据你的错误记录整理容易混淆的知识点。

模型故障不能显示为学生的知识问题。

### 7. 与 A 部分的边界

本阶段继续使用现有字段：

```text
problem_id
judge.passed
judge.status
judge.cases
cases[].errors[].type
analysis
```

不要增加 `question_id`。

A 尚未完全确定的以下字段，本阶段不得作为实现前提：

```text
difficulty
完整 knowledge_ids 字典
统一英文 error_type
题目推荐关系
```

如果当前题目存在 `knowledge_ids`，可以保存和展示，但误区追踪不能因为旧题没有该字段而失败。

本阶段不实现：

- AST 规则引擎
- 复杂误区知识库
- 模型训练
- 自动生成题目
- 同类题推荐
- 完整知识点掌握率
- 跨用户比较

### 8. 开发步骤

1. 检查当前 `git diff`，保留已有修改。
2. 先说明准备修改的文件及原因。
3. 先补测试，再修改实现。
4. 给 AI 输出模型增加固定 `misconception_tag`。
5. 增加标签校验和故障降级。
6. 保存分析结果。
7. 增加当前用户的统计接口。
8. 增加最小前端展示。
9. 运行后端测试、前端测试和构建。
10. 最后说明修改文件、数据流、测试结果和限制。

## 二、验收要求

### 1. 标签准确性

至少测试以下代码。

#### 循环边界

```python
total = 0
for i in range(1, 100):
    total += i
print(total)
```

在题目要求计算 1 到 100 时，应分类为：

```text
range_boundary
```

#### 累加逻辑

```python
total = 0
for i in range(1, 101):
    total = i
print(total)
```

应分类为：

```text
accumulation_error
```

#### 语法错误

```python
for i in range(1, 101)
    print(i)
```

应根据真实语法错误分类为：

```text
syntax_error
```

#### 变量问题

```python
name = input()
print("Hello, " + username + "!")
```

判题证据确认 `username` 未定义时，应分类为：

```text
variable_error
```

#### 证据不足

构造一个只有输出不一致、无法确认具体原因的提交，应分类为：

```text
other
```

不能强行猜测为某个具体误区。

### 2. 输出校验

- 模型返回自定义标签时，接口不能保存该标签。
- 最终保存的非空标签只能来自固定枚举。
- 标签、错因和三级提示必须与同一份判题证据一致。
- 不能出现“`sum` 以数字开头”这类与代码不符的解释。
- 隐藏测试内容不得泄露给前端或模型。

### 3. 历史记录

- 错误提交保存标签。
- 页面刷新后记录仍然存在。
- 退出并重新登录后记录仍然存在。
- 后来提交正确答案后，原错误记录不被删除。
- 正确提交不会新增误区记录。
- 运行代码但不提交，不会新增误区记录。

### 4. 用户隔离

创建两个用户进行测试：

- 用户 A 的误区统计只能看到 A 的记录。
- 用户 B 不能查看或影响 A 的记录。
- 使用其他用户的提交 ID 查询或修改时应被拒绝。

### 5. 重复误区统计

同一用户在两道不同题目中出现相同标签后：

```text
occurrence_count = 2
problem_count = 2
```

同一道题连续出现两次相同标签后：

```text
occurrence_count = 2
problem_count = 1
```

后来至少做对其中一道题时，错误次数仍然保留，同时“后来做对”统计发生变化。

### 6. 故障处理

模拟以下情况：

- Ollama 未启动
- 模型请求超时
- 模型返回非法 JSON
- 模型返回未知标签
- 模型返回空内容

必须满足：

- 程序判题结果不受影响。
- 提交记录仍能按现有规则保存。
- 不产生虚假的疑似误区统计。
- 前端显示可理解的降级提示。
- 接口不能因为 AI 故障返回无法处理的 500 错误。

### 7. 回归测试

至少运行：

```powershell
cd backend
python -m pytest -q
```

```powershell
cd frontend
node --test tests/*.test.cjs
npm run build
```

## 三、最终验收标准

学生提交错误代码后，系统根据真实判题证据生成一个受控的疑似误区标签；标签随个人提交记录保存；系统能够统计同一用户反复出现的误区，同时保留后来做对的事实；模型故障和其他用户的数据不会污染统计结果。
