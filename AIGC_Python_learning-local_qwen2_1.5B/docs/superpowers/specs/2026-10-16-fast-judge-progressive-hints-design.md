# 快速判题与异步三级提示设计

## 目标与边界

在不重写现有判题器的前提下，将确定性判题与 Qwen 学习反馈拆开：页面先展示程序判题结论和真实测试证据，失败时再生成三级提示。AI 只解释已经产生的证据，不能参与或改变判题。

第一版只实现两步请求、耗时记录、提示质量约束和三类错误验证。不引入 AST 规则引擎、复杂误区库、新模型、后台任务队列、SSE 或 WebSocket。

## 现有调用链

1. `CodeEditor.jsx` 调用 `POST /api/v1/code/submit`。
2. `coding.py::submit_code` 在线程池中调用现有 `judge_submission` 和 `run_code_process`。
3. 后端保存判题记录后，同一请求同步调用 `analyze_failure`。
4. 通过提交跳过 AI；语法错误走本地快速提示；其他失败由 Qwen 生成、本地检查、Qwen 复审。不合格时可能重新生成和复审。
5. 分析保存后整个响应才返回，前端因此无法先显示判题结果。

当前普通失败至少调用模型两次，最坏四次；生成请求还在用户消息中重复附带完整系统提示。

## 采用方案

采用两个有先后关系的 HTTP 请求。

### 第一步：确定性判题

`POST /api/v1/code/submit` 保留原有鉴权、题目校验、复习来源校验、程序判题、脱敏和记录保存。

- 通过：立即返回原始 `JudgeResult`，分析状态为 `skipped`，不调用模型。
- 语法错误：立即返回原始 `JudgeResult` 和本地快速提示，分析状态为 `ready`，不调用模型。
- 其他失败：立即返回原始 `JudgeResult`，分析状态为 `preparing`，此时不调用模型。

前端收到响应后立即显示通过与否、公开测试的预期输出、实际输出和运行错误。隐藏测试仍只展示通过状态。

### 第二步：学习提示

前端仅在状态为 `preparing` 时调用 `POST /api/v1/code/submissions/{submission_id}/analysis`。

后端按登录用户和提交编号读取数据库中已保存的题目编号、代码和脱敏判题结果，再调用现有 `analyze_failure`。接口不接受客户端提供的题目、判题结论或测试证据。

已有终态分析时直接返回保存结果，避免正常重试造成重复调用。前端等待时显示“正在准备提示”并保持判题区域可见。旧分析响应不得覆盖新提交或更新已卸载页面。

## 判题权威边界

- 不修改 `judge_submission` 和 `run_code_process`。
- 分析接口只返回分析和耗时，不生成新的判题结果。
- AI 输入来自已保存的服务端判题证据。
- 分析失败只更新分析状态，不修改 `passed`、`status`、测试输出或错误类型。

## 提示质量

语法错误继续依据 Python 的真实报错、行号和报错文本走固定快速路径。仅当报错行确实符合其他语言类型声明形式时才提示类型声明；不能因变量名为 `sum` 就声称语法错误。

三级提示要求：

1. 第一级只给一个简短思考方向，不含答案、具体修复或未经证实的诊断。
2. 第二级结合题目、代码和失败测试，指出要检查的位置或操作，术语随手解释。
3. 第三级给一个可执行的修改或验证思路，不提供完整正确代码。

每级只讲一个重点，避免“观察语句结构”等空话，不重复同一句建议。证据不足时明确说“目前只能确定……”或“尚不能确定……”。

保留 Pydantic schema、证据逐字匹配、答案泄露检查、本地分层与重复检查，以及用于识别无依据语义推断的独立 Qwen 审核。

取消不合格候选的整轮重新生成。普通失败最多一次生成和一次审核；本地检查失败时使用有证据边界的固定提示，审核发现无依据推断时不展示候选。通过和语法错误为零次模型调用。

## 耗时与输入输出优化

记录并持久化：

- `judge_ms`：程序判题墙钟耗时。
- `model_load_ms`：Ollama 返回的 `load_duration` 总和，缺失时为零。
- `hint_generation_ms`：生成、审核和本地检查的总墙钟耗时。

同时写结构化后端日志。第一版还会去掉用户消息中重复的系统提示，只发送失败用例所需字段并截断过长公开证据，将生成和审核输出上限缩短到当前 JSON schema 所需范围。若真实测试出现截断，再依据耗时和响应数据调整。

## 前端状态

1. `judging`：正在运行测试用例。
2. `preparing`：已经显示判题结果，同时显示“正在准备提示”，编辑器不因 AI 继续锁定。
3. `ready`：按顺序查看三级提示。
4. `unavailable`、`timeout`、`invalid_response`：保留判题结果并显示恢复说明。

## 修改文件

- `backend/app/api/coding.py`：拆分提交和分析接口，保存耗时。
- `backend/app/services/error_analysis.py`：准备状态、耗时、输入输出和调用次数，保留语法快速路径与质量检查。
- `backend/tests/test_submission.py`：两步流程、权威边界、耗时和三类错误。
- `frontend/src/components/codeApi.mjs`：新增分析请求。
- `frontend/src/components/CodeEditor.jsx`：先更新判题，再异步更新提示并防止旧响应覆盖。
- `frontend/src/components/SubmissionFeedback.jsx`：显示准备状态。
- `frontend/tests/submission-flow.test.cjs`：验证页面顺序和请求边界。

这些文件中已有用户未提交修改。实现只编辑与本设计相关的行并保留现有改动。

## 验证标准

- 语法错误：第一次响应为 `execution_error`，真实错误和行号立即可见，不调用 Qwen。
- 运行错误：第一次响应包含真实运行错误且状态为 `preparing`；第二次请求才生成提示。
- 输出错误：第一次响应为 `wrong_answer` 并显示真实预期和实际输出；第二次请求更新分层提示。
- 模拟 AI 给出与判题相反的说法，数据库和页面判题结论不变。
- 通过提交不发起分析请求。
- 前端在分析完成前已经渲染判题结果和“正在准备提示”。
- 页面卸载或出现新提交后，旧请求不再更新当前页面。

## 限制

- 第一版没有持久后台任务队列；分析请求中断后由相同接口重试。
- 同一提交只复用已保存的终态分析，不增加分布式锁。
- `model_load_ms` 依赖 Ollama 响应元数据；旧版本或测试替身缺失时记零。
- 自动测试验证流程、边界和文案；真实模型语言质量和冷启动耗时仍需在 Ollama 可用时现场验收。
