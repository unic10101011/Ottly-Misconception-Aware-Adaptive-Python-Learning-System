# 12 关学习闭环：实现契约草案 v0.1

日期：2026-10-13。依据：当前仓库静态代码检查与用户本次需求。

本文是实现与验收草案，不表示功能已经实现。仅新增本文档，不修改业务代码。文中的“已确认”来自用户要求；“建议值”和“待定”需要在对应开发任务开始前确定。旧调研文档中的 AI 自由出题、四级提示、15–20 关等设想不属于本期范围。

## 1. 目标与成功标准

已确认的目标：

1. 主线固定 12 关；学生可以直接提交当前代码，由后端程序判题。
2. 通常每题 3–4 个有效测试用例；第一关这种固定唯一输出题允许 1 个。所有必需用例和题面明确的教学约束通过，才算通过。
3. 主线通过后解锁下一关，不调用 AI；第 12 关通过后标记主线完成。
4. 未通过时提供三级提示：已覆盖的常见错误可用固定提示，其余调用 AI；AI 提示不合格或服务失败时用备用提示。
5. 保存代码、判题结果、知识点和可能的错误原因，支持按学生查看错题与后续改正情况。
6. 反复出现同类错误时，从审核过的现成题库推荐一道针对性加练题，不让 AI 在线自由生成题目、答案或测试用例。
7. 加练不影响主线闯关。主线连续失败和多道加练失败均可触发复习建议；建议不强制执行。

最小验收闭环：新学生进入第 1 关 → 提交正确代码 → 解锁第 2 关且 AI 调用数为 0 → 提交错误代码 → 获得三级提示并留下错误记录 → 达到重复错误条件 → 获得题库内加练 → 达到挫败条件 → 可跳过的基础关复习建议。刷新、重登后记录和进度保持一致。

## 3. 模块责任与不可违反的规则

### C-01：判题拥有唯一的通关决定权

- 后端题库拥有标准答案、私有用例、比较规则及教学约束；客户端不能提交或覆盖这些字段。
- `execution_success` 只表示代码运行没有异常，不能当作 `accepted`。
- `accepted` 当且仅当全部必需用例通过且所有已公开的教学约束满足。
- AI 只能生成解释、候选错因和提示，无权修改判题结论、进度、测试用例或推荐题库。
- 不能按学生代码是否与参考代码相同判对错；允许符合题面约束的不同正确写法。
- 学生代码超时属于一次失败；判题服务不可用、数据库故障等属于系统错误，不能算学生答错。

### C-02：运行与提交分离

- “运行”可保留为试运行，不解锁、不计入失败次数、不触发 AI 或推荐。
- “提交”无需先运行，始终判定本次请求的代码快照，不复用旧运行结果。
- 正常判题状态至少包括 `accepted / wrong_answer / syntax_error / runtime_error / time_limit / memory_limit / output_limit / constraint_violation / disallowed_operation / system_error`。
- 系统配置的资源上限由后端决定，客户端不得扩大；具体限额在执行环境确定后固定。
- 用例执行不得共享学生变量或输出；超时必须回收执行单元。限制网络、宿主文件访问及其他不必要能力，不能把现有 AST 检查当作隔离边界。

### C-03：主线进度单向推进

- 新学生仅第 1 关可进入；第 n 关通过后解锁 n+1，已通过关卡可复习。
- 后端拒绝尚未解锁的主线提交，前端隐藏按钮不足以作为校验。
- 已通过关卡后来提交失败，不回退进度、不重新锁关。
- 同一提交重复请求或同一关重复通过，不重复增加通关数。
- 加练通过、失败、跳过及复习建议，均不能直接解锁或锁定主线。

### C-04：提示按规则、AI、备用顺序产生

1. 主线或加练通过：`feedback=null`，模型调用次数为 0。
2. 学生提交失败且命中具备可信证据的固定规则：使用对应三级固定提示，来源为 `rule`。
3. 其他学生提交失败：向 AI 提供题目公开信息、本次代码、判题证据和允许的错因列表。
4. AI 超时、不可用、空回答、JSON/schema 不合格或证据校验失败：使用对应知识点的审核过的三级备用提示，来源为 `fallback`。
5. 对 `disallowed_operation` 直接给运行环境限制说明，不将其自动诊断为知识误解。`system_error` 显示稍后重试，不调用教学 AI、不累计学习失败。

提示级别：

| 级别 | 内容 | 示例：疑似循环边界错误 |
|---|---|---|
| L1 | 指向相关概念或提出观察问题 | “想一想 range 的结束值会不会被包含。” |
| L2 | 结合有效证据缩小检查位置 | “检查循环范围这一行，并列出它会产生的最后两个数。” |
| L3 | 给出具体修改思路或步骤 | “题目要求包含终点，请调整范围，让最后一个需要的数也参与计算，再用小输入验证。” |

建议界面初始展示 L1，学生主动展开 L2、L3；展开不重新调用模型。三级提示不直接提供整题可提交答案。对第一关这样的一行题，提示也应保持概念或操作说明，避免直接显示完整答案。

AI 输出必须先完整接收并校验，再展示；不得把未校验流式内容直接输出到学生界面。AI 的自然语言正确性不能仅凭 JSON 合法保证，还需人工审核样例集和回归测试；检测到问题就回退，但不能宣称自动校验能消除所有幻觉。

### C-05：错误事实与原因推测分开保存

- 判题状态、异常类型、失败用例、实际输出属于事实；“把 range 上界理解为包含”属于可能原因。
- 规则或 AI 的原因必须附证据引用；证据不足可记录 `unknown`，不得为了填字段强行归因。
- `SyntaxError` 不能直接等同于“学生不懂循环”；必须区分报错类型、知识点和候选错因。
- 本期建议只将有匹配规则及执行证据支持的错因计入自动加练触发；AI 独立推测可展示和保存，但暂不作为强制统计依据。模型自报高置信度不等于已经验证。
- 正确提交也要保存，用于判断是否改正、重置相关计数；后续通过不能抹掉原始错误历史。

## 4. 题库契约

题目可以先用版本化 JSON/YAML 配置维护，不必同时建设题库管理后台。主线与加练共用判题结构，通过 `kind` 区分。

| 字段 | 约束 |
|---|---|
| `problem_id, version` | 稳定标识与题目版本；提交记录绑定具体版本 |
| `kind` | `main` 或 `practice` |
| `level_no` | 主线为 1–12 且唯一，加练为空 |
| `title, statement, starter_code` | 题面、脚手架；必须说明输入输出与必要语法限制 |
| `knowledge_ids` | 使用固定知识点字典，不允许 AI 临时发明 ID |
| `target_misconception_ids` | 加练目标错因；主线可为空 |
| `prerequisite_knowledge_ids` | 选加练时避免引入学生尚未学过的前置知识 |
| `review_level_ids` | 对应已可访问的基础关卡，用于复习建议 |
| `execution_mode` | 第一关可为 `stdout`；后续建议统一 `stdin_stdout`，待题纲确定 |
| `tests` | 每项含 `case_id, stdin, expected_stdout, visibility`；非固定输出题通常 3–4 项 |
| `comparison_policy` | 每题明确定义；建议统一换行符并忽略一个终止换行，保留其余空白，不使用无差别 trim |
| `constraints` | 仅包含题面公开、可机械验证的教学约束；如“必须使用 for” |
| `limits` | 由服务端固定的时间、内存、输出长度上限 |
| `reference_solution` | 仅服务端和内容审核使用 |
| `fallback_hints` | 经审核的 L1/L2/L3；规则命中时可有更具体的模板 |
| `reviewed` | 只有完成内容与执行验证的题目可发布、可推荐 |

题库准入：参考解通过全部用例；至少一组针对目标错因的典型错误解被拒绝；输入覆盖普通情况及与本知识点有关的边界；每个用例有实际区分价值，不重复运行同一个固定输出凑数量。

第二关需要特别决策：现题是“求 1 到 100 的和”，结果固定。建议改为“输入 n，使用 for 计算 1 到 n 的和”，示例测试可用 n=1、2、10、100，对应 1、3、55、5050；这样 4 个用例才有独立意义。这是题面修改建议，尚未确定采用。若保留固定题面，应单独写明它是固定输出例外，并明确是否机械检查 for 约束。AST 约束能检查约定语法，不能证明学生真正理解知识点。

尚需补齐 12 关的完整题纲；当前仓库不能确定后 10 关内容。应先列出每关知识点、题面、前置知识、用例、参考解、常见错因、三级备用提示、复习映射。加练题也需要实际编写或整理并审核，当前代码没有可直接调用的加练题库。

## 5. 学习记录与推荐契约

### 最小持久化对象

| 对象 | 最少记录内容 |
|---|---|
| `Submission` | 用户、题目及版本、主线/加练来源、代码快照、请求去重键、判题状态、用例执行结果、提交时间 |
| `Feedback` | 提交 ID、知识点、候选原因、证据、原因来源与是否可计数、三级提示、提示来源、回退原因、规则/提示版本 |
| `LevelProgress` | 用户、关卡、首次通过时间、对应提交；唯一约束避免重复通关 |
| `Recommendation` | 用户、类型、触发规则与版本、证据提交 ID、目标题目或复习关卡、状态、创建时间 |

不要求初期每个概念都独立建表：反馈可与提交一对一，学习汇总可从提交推导；错题列表可查询失败记录并附上后续通过状态。无需立即增加知识追踪模型或掌握度百分比。

所有学习接口从验证后的登录凭证获得用户身份；不信任请求中的 `user_id`，不能继续默认用户 1。题目、进度、提交、提示、推荐读取均检查归属。最终判题记录与主线通关更新在同一事务保存；AI 失败不回滚它们。

### 建议的第一版推荐规则（阈值尚待确认）

已确认：主线连续失败与多道加练失败，两种情况都允许触发复习建议。下表中的 3、5 等数字是建议值，不是用户已确定的要求。

| 规则 | 建议触发口径 | 结果 |
|---|---|---|
| R1 同类错误加练 | 最近 5 次有效、非重复的计数提交中，同一“知识点＋有证据支持的错因”出现至少 3 次；从最近一次该知识点相关题目通过后开始累计 | 推荐 1 道匹配错因的已审核加练 |
| R2 主线挫败 | 当前尚未通过的主线关卡连续 3 次有效失败；通过后归零 | 推荐相关基础关复习 |
| R3 加练挫败 | 同一知识点下连续完成的 3 道不同加练题均未通过；相关加练通过后归零 | 推荐相关基础关复习 |

计数定义建议：

- 有效失败包括错误输出、语法错误、运行错误及学生代码资源超限、教学约束未满足；系统错误、未授权/锁关请求、单纯试运行不计数。运行环境禁止操作记录但不参与知识错因计数。
- 相同请求去重键必须只产生一条提交。相同用户、题目版本与相同代码的重复提交可以留操作记录，但在代码未改变且已有相同判定时不重复推进上述计数，避免连续点击造成错误推荐。
- R1 的滚动窗口按正式提交顺序计算，不因一次有多个失败用例而多计。
- R3 的“一道题没做出来”建议定义为：至少有一次有效失败后，学生点击“暂时跳过”结束本轮加练；正在改代码不应立刻算放弃。直接退出或无提交跳过不记失败。重复同一道加练不充当多道不同题。
- 阈值刚达到时产生推荐；同一原因存在待处理推荐时更新证据，不重复堆卡片。通过、跳过、取消均记录状态；跳过后建议至少再发生 3 次相关有效失败才重新推荐，具体间隔待定。
- 若同时触发 R1 与 R2/R3，优先展示复习建议，加练仍为可选入口；不自动跳页、不遮断编辑器。
- 推荐题需匹配目标知识点与错因，前置知识已满足；优先选未做过、难度合适的题。没有合适题时返回“暂无匹配加练”，可以附已有基础关复习入口，绝不临时让 AI 编题。
- 第一关找不到更早基础关时，可建议回看本关知识说明；不得返回不存在或未解锁的复习目标。
- 加练题数量需支撑“多道不同题”的规则；只有一道匹配题时不能伪造三道失败事件。

## 6. 前后端接口草案

沿用项目 `/api/v1` 前缀。下面是建议新增接口，尚未实现。

| 接口 | 责任 |
|---|---|
| `GET /levels` | 返回 12 关公开信息及当前用户进度 |
| `GET /problems/{problem_id}` | 返回可访问题面、脚手架、公开样例，不返回参考解或隐藏用例 |
| `POST /submissions` | 验证身份/权限/去重 → 后端判题 → 保存记录与进度 → 失败时获取并保存提示与推荐 |
| `GET /submissions/{submission_id}` | 获取本人提交结果，恢复网络中断后的页面 |
| `GET /mistakes` | 本人错题、知识点、可能原因、是否已通过；支持分页 |
| `GET /recommendations` | 本人当前加练/复习推荐及理由 |
| `POST /recommendations/{id}/actions` | 记录开始、暂时跳过、忽略等动作；通过状态由后端判题写入 |

`POST /submissions` 的建议请求：

```json
{
  "request_id": "client-generated-unique-id",
  "problem_id": "main-02",
  "problem_version": 1,
  "code": "n = int(input())\ns = 0\nfor i in range(1, n):\n    s += i\nprint(s)",
  "recommendation_id": null
}
```

`problem_version` 用于发现题目已更新，客户端无权指定旧版绕过判题；版本不匹配返回明确冲突并要求刷新。`kind` 由后端题库确定，主线不能靠改请求变成加练。主线复习仍按主线题目提交，但不重新锁关或重复解锁。


通过时 `judge.status=accepted`、`feedback=null`，主线首次通过返回新解锁关卡；重复通过、加练通过、第 12 关通过不返回不存在的新关卡。第 12 关通过令 `main_completed=true`。

业务未通过仍是成功完成判题的 HTTP 200；无认证用 401、锁定用 403、资源不存在用 404、去重键不同请求体或题目版本冲突用 409、无效请求用 422，基础设施错误用 5xx 或可恢复的 `system_error`，不能伪装成 `wrong_answer`。

去重范围为当前用户加 `request_id`，相同键不同内容拒绝；并发重复请求只允许一个判题任务和一组有效学习更新。先提交判题及进度事务，再请求模型；为 AI 设置有限超时（建议 8 秒、初期不重试，数值待实测）。刷新、网络重试、进程中断后可按请求键找到原提交；若提示尚未完成，恢复时可直接保存备用提示，避免无限等待或重复触发模型。

隐藏用例的具体输入、标准输出、参考解不进入学生接口或 AI 可展示内容。需要具体反例时使用公开样例或审核过的可公开诊断用例。服务器可保存完整执行证据，学生接口仅返回允许公开的字段和汇总。

## 7. AI 输入输出契约

学习提示应有独立的服务函数，不把本次任务交给无约束的普通聊天页。已有模型 HTTP 调用可整理复用，但须用真实服务返回格式验证适配；不能直接假定现有 SSE 解析能返回所需 JSON。

输入由后端构造：公开题面、知识点字典、该次代码快照、确定性判题状态、允许公开的失败证据、规则候选、允许错因枚举、三级提示定义。将学生代码与注释作为待分析数据，不作为模型指令；不传登录信息或无关学生历史。

AI 只返回：

```json
{
  "possible_cause_id": "UNKNOWN",
  "evidence": [],
  "hints": [
    {"level": 1, "text": "..."},
    {"level": 2, "text": "..."},
    {"level": 3, "text": "..."}
  ]
}
```

必需校验：字段类型及额外字段、错因在允许枚举内、提示恰好包含 1/2/3 且非空、提示长度上限、行号确实位于本次代码内、case_id 来自允许证据、引用内容与记录一致。非 UNKNOWN 的归因至少有有效证据引用，但“引用存在”本身仍不证明原因正确。

禁止模型返回通关决定、解锁决定、新题目或新测试。提示不得包含完整参考答案或未公开测试；自动检查能发现的泄漏与明显矛盾应拒绝。字段错误、未知行号、无关用例、截断回答和已发现的答案泄漏都整组回退，不能把坏的 L2 混进好的 L1。

提示来源统一为 `rule / ai / fallback`，错因来源另存，避免把“AI 润色规则提示”误记成“AI 证明错因”。缓存绑定提交及提示版本，学生修改代码后的新提交不沿用旧证据。

## 8. 验收用例

| 编号 | 输入或操作 | 必须观察到 |
|---|---|---|
| T01 | 新用户打开地图，直接请求尚未解锁关卡提交 | 仅第 1 关解锁，后端拒绝越关 |
| T02 | 不点击运行，直接提交正确代码 | 正常判题；首次通过解锁下一关；模型调用次数为 0 |
| T03 | 先运行代码 A，再改成错误代码 B 并提交 | 判定 B，不能复用 A 的结果 |
| T04 | 在多输入求和题提交 print(5050) | 至少一个用例失败，不能通关 |
| T05 | 不同正确实现，且符合题面教学约束 | 全部通过；不能要求字符串匹配参考代码 |
| T06 | 仅部分测试通过，或违反题面明确的 for 约束 | 未通过，且说明具体失败类型 |
| T07 | 提交缺少冒号等常见错误 | 产生错误记录与固定三级提示；无需 AI |
| T08 | 提交规则未覆盖的错误；AI 返回合格结构 | 使用本次代码和判题证据生成三级提示，来源 ai |
| T09 | AI 超时、乱 JSON、伪造行号、未知错因或已检测的整题答案泄漏 | 及时返回三级备用提示；判题及错题记录仍然存在 |
| T10 | 请求超时后用同一 request_id 重试，含并发请求 | 不重复通关、不重复统计错误、不重复产生推荐 |
| T11 | 达到 R1 阈值；以及仅达到阈值减一 | 前者推荐匹配的已审核加练，后者不触发 |
| T12 | 同一道题不改代码反复点击提交 | 不刷高推荐计数；一题的多个失败用例只计一次 |
| T13 | 主线连续失败达到 R2；三道不同加练失败并暂时跳过达到 R3 | 两条路径各自产生可跳过的复习建议；跳过不重复弹出 |
| T14 | 连续失败中插入相关正确提交、系统错误或仅试运行 | 正确提交重置相关连续计数；系统错误和试运行不计入 |
| T15 | 加练通过、失败或跳过 | 主线解锁状态完全不变 |
| T16 | 没有合适的加练题，或没有更早的基础关 | 返回明确空结果或有效复习入口，不调用 AI 编题 |
| T17 | 第 12 关通过；刷新；重登；重交已通过关卡 | 主线完成状态保存，不产生第 13 关，不回退 |
| T18 | 用户 A 读取用户 B 的提交、提示与推荐 | 拒绝访问，记录不会归到默认用户 1 |
| T19 | 死循环、超大输出、内存超限、多用例并行执行 | 执行单元可回收；限制生效；输出与变量互不污染；服务继续可用 |
| T20 | 查询学生接口和提示上下文 | 无参考解、隐藏用例明细或他人记录泄漏 |

推荐规则测试使用小型人工序列逐项验证“计数、去重、重置、跳过”，AI 测试使用可控的模拟响应覆盖失败路径；实际模型另用人工审核样例验证提示质量，不要求每次措辞完全相同。

## 9. 实施顺序与待定项

1. 确定 12 关题纲、输入模式、教学约束、错因字典和计数阈值；先完成两关及关联加练的审核内容。
2. 补身份校验、执行隔离、题库加载和真正的后端判题，完成提交与主线进度持久化。先跑通两关确定性闭环。
3. 接入固定三级提示、AI 结构化提示与备用提示，覆盖超时及坏输出；不把 AI 当作判题前置条件。
4. 接入错题查询、规则推荐、加练和复习建议，用提交序列测试规则。
5. 使用同一题目结构补全 12 关与加练内容，前端使用统一页面呈现，完成全链路验收。

实施前仍需确定：

- 12 关的具体知识点与排序；是否保留现有第 2 关的位置和题面。
- 是否采用 stdin 输入方案，哪些关要求特定语法。
- R1/R2/R3 的数值阈值、暂时跳过作为加练失败结束事件的口径、跳过后再次推荐间隔。
- 代码执行部署环境与资源上限，以及 AI 超时预算。

这些选择不阻止先审核现有代码与编写本草案，但不应被实现人员默认为已确认需求。
