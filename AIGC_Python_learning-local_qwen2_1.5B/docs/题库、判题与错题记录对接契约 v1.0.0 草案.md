# 题库、判题与错题记录对接契约 v1.0.0

更新日期：2026-10-16。代码基线：main 的 `d4a964f`，包含本轮契约实现及已合入的账号、进度更新。文件名保留“草案”便于沿用已有链接，正文已按当前实现更新，可用于题库、后端和错题模块对接。

本文件定义当前字段、接口和兼容行为；数据库操作详见 [实施与迁移说明](05-契约v1实施与迁移.md)，可直接消费的实际返回见 [接口响应样例](contract-v1-examples.json)。模型教学分析的提示词、参数及生成审核流程未在本轮调整，知识点编号由接口适配层确定性映射。

当前主线开放第 1 关和新版第 2 关；第 3 关为待开放槽位。旧 `level2` 循环题继续兼容，不代表新版第 2 关通过。后续题目内容发布及项目数据库迁移是独立操作，不能仅凭代码更新推断已经完成。

**1. 三方共同遵守的约定**

| 项目 | 统一约定 |
|---|---|
| 题目唯一标识 | 使用 `problem_id`，不再同时使用 `question_id` |
| 字段命名 | 全部使用英文 `snake_case` |
| 字符编码 | UTF-8 |
| 时间 | UTC，ISO 8601，毫秒精度，例如 `2026-10-16T00:10:08.000Z` |
| 执行耗时 | 秒，字段为 `execution_time` |
| 行号 | 从 1 开始，无法定位时为 `null` |
| 空集合 | 返回 `[]`，不返回 `null` |
| 可空字段 | 明确返回 `null`；隐藏测试字符串按第 7 节清空为 `""` |
| 用户身份 | 后端从登录令牌获取；客户端不得提交 `user_id` |
| 判题依据 | 后端正式测试结果 |
| AI 职责 | 提供疑似原因与提示，不修改判题结果 |
| 历史记录 | 保存提交时的题目信息与结果，不能被新题目版本覆盖 |

客户端应忽略不认识的响应字段；正式提交请求继续禁止未经定义的额外字段。

本契约覆盖 `/api/v1/code/*` 学习接口，不将认证、账号管理和聊天接口改为相同响应格式。学习接口的成功响应外层统一为 `{schema_version, code, data}`，运行接口额外保留 `msg`；错误响应沿用 FastAPI 的 `detail`。

**2. 标识和版本规则**

这里区分三个概念：

| 字段 | 类型 | 示例 | 含义 |
|---|---|---|---|
| `schema_version` | string | `"1.0.0"` | 数据契约版本 |
| `problem_id` | string | `"greeting-v1"` | 某一个题目版本的唯一标识 |
| `version` | integer | `1` | 题目版本号 |
| `level_no` | integer | `2` | 当前教学顺序 |

新题目 ID 采用：

```text
<英文短名称>-v<正整数>

greeting-v1
shell-shop-v1
greeting-v2
```

规则：

- 短名称使用小写字母、数字和连字符。
- `problem_id` 最多 100 字符。
- `greeting-v2` 的 `version` 必须为 `2`。
- `level_no` 不放进唯一标识；调换教学顺序不应改变题目身份。
- 现有 `level1`、`level2` 保留为历史兼容 ID，不照此规则重命名。
- 数据库快照列名为 `problem_version`，对外返回名为 `version`。正式提交只传 `problem_id`，由后端读取对应版本。
- 响应外层 `schema_version` 表示当前接口格式；历史记录内同名字段表示当时保存的格式，旧记录可以为 `null`。

版本升级规则：

| 修改内容 | 是否升级题目版本 |
|---|---|
| 页面颜色、布局、纯错别字修正 | 否 |
| 输入范围、任务要求、输出格式 | 是 |
| 正式测试输入或预期输出 | 是 |
| 判题比较方式、执行限制 | 是 |
| 知识点、前置知识、难度 | 是 |
| 参考解或提示的教学含义 | 是 |

升级时新增题目版本，保留旧版本供历史查询和复习。不同版本分别统计，不自动继承通关。

上述“哪些修改需要升版”属于团队发布规则。当前加载器自动校验 ID 后缀与版本一致，但不会自动比较 Git 历史、发现题意变化或替出题人升级版本。

`schema_version` 使用三段版本：

```text
主版本.次版本.修订版本
```

- 删除字段、改类型、改已有字段含义：升级主版本。
- 新增可选响应字段：升级次版本。
- 不改变结构和语义的修正：升级修订版本。

**3. 题目内容契约**

以下是服务端保存的完整题目结构。表中字段均必填。

| 字段 | 类型 | 规则 |
|---|---|---|
| `schema_version` | string | 本版为 `"1.0.0"` |
| `problem_id` | string | 题目版本唯一标识 |
| `version` | integer | ≥1 |
| `level_no` | integer | 主线关卡为 1～12 |
| `title` | string | 非空 |
| `difficulty` | integer | 只能为 1、2、3 |
| `knowledge_ids` | string[] | 至少一个，无重复 |
| `prerequisite_knowledge_ids` | string[] | 可以为空，无重复 |
| `prerequisite_problem_ids` | string[] | 实际解锁所需的前置题目，可以为空 |
| `published` | boolean | 是否允许普通题目访问和提交 |
| `story` | string | 情境 |
| `teaching` | object[] | 至少一项知识点讲解 |
| `description` | string | 完整任务及输入输出约束 |
| `starter_code` | string | 初始代码，可以为空 |
| `examples` | object[] | 至少一个输入输出样例 |
| `tests` | object[] | 至少一个正式测试 |
| `comparison` | string | `exact` 或 `legacy_trim` |
| `time_limit_seconds` | integer | 本阶段统一为 `3` |
| `output_limit_chars` | integer | 本阶段统一为 `8000` |
| `hints` | object | 固定三级提示 |
| `reference_solution` | string | 至少一个可通过正式测试的参考解 |
| `solution_explanation` | string | 参考解详解 |

以下是嵌套字段片段，不是可直接加载的完整题目文件；完整实例见 `backend/app/data/greeting-v1.json`。

```json
{
  "teaching": [
    {
      "title": "读取输入",
      "text": "input 每次读取一行文字。",
      "example": "name = input()"
    }
  ],
  "examples": [
    {
      "stdin": "Tim\n",
      "stdout": "Hello, Tim!\n"
    }
  ],
  "tests": [
    {
      "case_id": "sample-1",
      "stdin": "Tim\n",
      "expected_output": "Hello, Tim!\n",
      "visibility": "public"
    }
  ],
  "hints": {
    "level1": "思考方向",
    "level2": "相关知识与检查位置",
    "level3": "修改或验证思路"
  }
}
```

测试约束：

- `case_id` 在同一 `problem_id` 内唯一，跨题目可以重复。
- `visibility` 只能是 `public` 或 `hidden`。
- 正式测试顺序固定，返回结果按此顺序排列。
- 新接入题目使用 `exact`；`legacy_trim` 仅用于兼容旧题。
- `exact` 仅统一 `\r\n` 为 `\n`，不删除空格或末尾换行。
- 一般输入题应包含至少一个公开测试和一个隐藏测试。
- 发布前必须确认参考解通过全部正式测试。

加载器还会拒绝重复题目 ID、重复知识点引用、不存在的前置题以及循环依赖。完整题目字段不接受额外键。当前 `TestCase` 的 `stdin` 和 `visibility` 允许省略，分别默认为 `""` 和 `public`；出题文件建议显式填写。

当前执行限制固定为每个测试用例 3 秒，stdout 和 stderr 各自最多 8000 字符；没有定义内存限额。代码在短生命周期子进程中运行，该沙箱用于本机演示，不构成恶意代码的操作系统隔离边界。

这里保留样例的 `stdout` 和正式测试的 `expected_output`，避免为了改名增加迁移工作。

**4. 知识点、前置知识与难度**

知识点由题库维护统一字典：

```json
{
  "knowledge_id": "K02",
  "name": "变量、输入与字符串拼接",
  "description": "理解变量赋值，读取文本输入，并使用变量拼接字符串。",
  "aliases": ["输入与变量", "变量", "赋值", "变量先赋值后使用", "字符串拼接", "字符串拼接与输出格式"]
}
```

约定：

- 编号沿用 `K01`～`K12`，名称与解释由题库负责人统一维护。
- 后端校验题目中的知识点 ID 必须存在。
- AI 和错题模块不能自行创建编号。
- 修改知识点名称不改变编号；改变其教学含义需要重新评估关联题目版本。
- 字典文件为 `backend/app/data/knowledge.json`；`aliases` 是内部精确别名表，通过 `GET /api/v1/code/knowledge` 返回时不包含它。
- 名称和别名去掉首尾空白并统一大小写后，不允许同时指向不同编号。

两个前置字段各有用途：

```json
{
  "prerequisite_knowledge_ids": ["K01"],
  "prerequisite_problem_ids": ["level1"]
}
```

- `prerequisite_knowledge_ids`：描述教学依赖。
- `prerequisite_problem_ids`：控制实际解锁，要求全部通过。

**本阶段不根据“知识点已掌握”的推测自动解锁。**

当前活跃关卡在 `backend/app/data/levels.json` 中配置。有 `problem_id` 的槽位从题目文件读取发布状态和前置关系，禁止重复维护另一份前置配置；`problem_id=null` 是待开放槽位，可配置已知前置题目。旧循环题保留在题库中，但不占新版第 2 关槽位。

难度统一为：

| `difficulty` | 名称 | 定义 |
|---|---|---|
| `1` | 基础 | 直接应用本关新知识，步骤明确 |
| `2` | 巩固 | 组合多个已学操作，需要自行组织步骤 |
| `3` | 综合 | 组合多个知识点，需要分解问题和处理多种情况 |

第 2 关“打招呼”定为 `1`。

难度由题库负责人指定；它不是学生能力分数，也不随某次提交失败而改变。

**5. 运行和正式提交接口**

统一前缀：

```text
/api/v1
```

统一请求头：

```http
Authorization: Bearer <access_token>
Content-Type: application/json
```

运行接口：

```http
POST /api/v1/code/run
```

```json
{
  "code": "name = input()\nprint(\"Hello,\", name + \"!\")",
  "stdin": "Tim\n",
  "timeout": 3
}
```

约定：

- `stdin` 可省略，默认 `""`。
- `timeout` 可省略，默认 10 秒，允许 1～10 秒。
- `code` 长度为 1～20000 字符；当前运行接口只校验长度，页面会拒绝全空白代码。
- `stdin` 最多 8000 字符。
- 运行不保存正式提交、不生成错题、不解锁关卡、不调用教学分析。
- 运行成功只表示程序执行成功，不代表答案正确。

运行响应的 `data` 为：

```text
RunResult {
  success: boolean,
  output: string,
  output_available: boolean,
  errors: object[],
  execution_time: number
}
```

`errors[].type` 使用第 6 节规范错误码；运行错误对象可以额外包含 `column`、`suggestion` 等既有字段，不要求与正式判题的 `ExecutionError` 完全同形。没有输出时 `output=""`；执行终止且未采集输出时 `output_available=false`。

正式提交：

```http
POST /api/v1/code/submit
```

```json
{
  "problem_id": "greeting-v1",
  "code": "name = input()\nprint(\"Hello,\", name + \"!\")"
}
```

约定：

- 只接受 `problem_id`、`code`。
- `code` 为 1～6000 字符，不能全为空白。
- 版本通过 `problem_id` 唯一确定，不重复传 `version`。
- 不允许客户端传测试、答案、难度、用户 ID 或通过状态。
- 每个正式测试独立执行。
- 判题和分析完成后一次性返回，本版不增加异步轮询接口。

从错题页重做时，额外传：

```http
X-Review-Source-Id: 123
```

`123` 必须是当前用户、同一 `problem_id` 的失败提交。没有这个请求头的普通提交，不统计为“复习提交”。

有效复习来源允许继续提交已下线版本或不再满足当前前置条件的旧错题。后端在判题前校验来源，并在保存前重新校验账号与来源仍然存在，避免账号注销后产生残留记录。

**6. 判题与错误分类契约**

提交成功返回：

```text
{
  schema_version: "1.0.0",
  code: 200,
  data: {
    submission_id: integer,
    problem_id: string,
    version: integer,
    created_at: string,
    error_type: string | null,
    judge: JudgeResult,
    analysis: AnalysisResult
  }
}
```

`JudgeResult`：

| 字段 | 类型 | 规则 |
|---|---|---|
| `status` | string | 固定四种状态，见下表 |
| `passed` | boolean | 是否全部通过 |
| `passed_cases` | integer | 通过用例数量 |
| `total_cases` | integer | 正式用例总数，必须 ≥1 |
| `failed_tests` | string[] | 失败用例的 `case_id`，按测试顺序排列 |
| `cases` | object[] | 全部测试结果 |

固定关系：

```text
total_cases = cases.length
passed_cases = passed=true 的用例数
failed_tests = passed=false 的用例 ID 列表
passed = passed_cases == total_cases
```

`failed_tests` 由后端生成，不单独维护另一份可修改的数据。

状态与优先级：

| 状态 | 判定条件 |
|---|---|
| `accepted` | 全部通过 |
| `timeout` | 任一用例超时 |
| `execution_error` | 没有超时，但存在执行或代码检查错误 |
| `wrong_answer` | 没有上述错误，但存在输出不匹配 |

单个结果：

```text
CaseResult {
  case_id: string,
  passed: boolean,
  visibility: "public" | "hidden",
  expected_output: string,
  actual_output: string,
  output_available: boolean,
  errors: ExecutionError[],
  execution_time: number
}

ExecutionError {
  type: string,
  line: integer | null,
  message: string
}
```

`error_type` 和 `errors[].type` 统一使用以下英文错误码：

| 错误码 | 含义 |
|---|---|
| `WRONG_ANSWER` | 输出不匹配 |
| `SYNTAX_ERROR` | 语法错误 |
| `INDENTATION_ERROR` | 缩进错误 |
| `NAME_ERROR` | 变量或名称未定义 |
| `TYPE_ERROR` | 类型使用错误 |
| `VALUE_ERROR` | 值不符合操作要求 |
| `ZERO_DIVISION_ERROR` | 除数为零 |
| `INDEX_ERROR` | 索引越界 |
| `KEY_ERROR` | 字典键不存在 |
| `ATTRIBUTE_ERROR` | 属性不存在 |
| `EOF_ERROR` | 输入已耗尽 |
| `IMPORT_ERROR` | 允许范围内的导入失败 |
| `SECURITY_ERROR` | 使用禁止操作 |
| `OUTPUT_LIMIT_EXCEEDED` | 输出超限 |
| `TIMEOUT` | 执行超时 |
| `RUNTIME_ERROR` | 其他学生代码执行错误 |

中文解释放在 `message` 中，程序不要靠匹配中文判断类型。

提交级 `error_type` 的确定规则：

1. 通过：`null`。
2. 总体超时：`TIMEOUT`。
3. 总体执行错误：按测试顺序取第一个执行错误的规范化错误码。
4. 仅输出不匹配：`WRONG_ANSWER`。

执行器、数据库等系统故障不放进上述学生错误码，返回 HTTP 5xx，不记为学习失败。

已知执行器故障 `RunnerError` 返回 HTTP 503，且不新增提交记录。判题已经入库后发生的分析调用异常则返回 `analysis.status=unavailable` 并保留判题；不能把所有 5xx 都理解为“肯定没有提交记录”。对缩进错误的进一步区分在接口层通过只读 AST 解析完成，不改变发给模型的原始错误名称。

**7. 隐藏测试与输出保护**

学生端和教学分析端都只能接收脱敏后的结果。

隐藏测试处理：

```json
{
  "case_id": "hidden-1",
  "passed": false,
  "visibility": "hidden",
  "expected_output": "",
  "actual_output": "",
  "output_available": false,
  "errors": [],
  "execution_time": 0.001
}
```

上面的耗时只是示例。

约定：

- 不返回隐藏输入、预期输出、实际输出和异常详情。
- 可以返回测试 ID、通过状态、耗时，以及提交级的规范错误码。
- 教学分析不能引用被隐藏的输入输出。
- 历史记录中的判题 JSON 保存脱敏版本。
- `output_available=false` 不等于“程序没有输出”。

前端显示顺序必须是：

```text
隐藏测试 → “隐藏测试仅展示通过状态”
公开测试且输出不可用 → “输出未采集”
公开测试且输出为空 → “无输出”
其他 → 显示实际输出
```

**8. 分析、知识点和三级提示契约**

```text
AnalysisResult {
  status: "ready" | "skipped" | "unavailable" | "timeout" | "invalid_response",
  source: "ai" | "fixed" | null,
  model: string | null,
  message: string,
  content: AnalysisContent | null
}

AnalysisContent {
  suspected_cause: string,
  knowledge_ids: string[],
  knowledge_points: string[],
  evidence: Evidence[],
  hints: {
    level1: string,
    level2: string,
    level3: string
  }
}

Evidence {
  case_id: string,
  field: "actual_output" | "error_message",
  quote: string,
  explanation: string
}
```

规则：

- `ready` 时 `content` 必须非空；其他状态必须为 `null`。
- 通过时使用 `skipped`，`source=null`、`model=null`。
- AI 分析成功使用 `source=ai`。
- 采用基础提示使用 `source=fixed`、`model=null`。
- `knowledge_ids` 由后端从题目知识点及前置知识中校验，不接受模型任意编号。
- `knowledge_points` 保留原模型或基础提示提供的知识点文字，不替换成字典名称。
- 对这些文字去掉首尾空白、统一大小写后，按字典名称或别名精确匹配，再限制在本题 `knowledge_ids` 与 `prerequisite_knowledge_ids` 范围内，按首次出现去重得到分析的 `knowledge_ids`。
- 未匹配或超出范围的文字不生成编号；没有匹配则为 `[]`。不做模糊猜测，也不额外调用模型分类。
- 两个数组不承诺长度相同或逐项对应。错题模块不得按数组索引关联编号与文字。
- `evidence` 为 1～3 条，必须引用真实、可公开的结果。
- `suspected_cause` 使用“疑似”等措辞，不能当作已确诊的误概念。

分析知识点文字为 1～4 项；三级提示、疑似原因和证据解释沿用原有格式、证据和质量校验。公开样例通过而隐藏测试失败时，基础提示可以引用公开样例，但不能据此推断隐藏测试内容。

三级提示职责固定：

| 等级 | 内容 | 不应包含 |
|---|---|---|
| 第 1 级 | 提醒思考相关概念 | 完整答案、具体替换代码 |
| 第 2 级 | 相关知识与检查位置 | 完整答案 |
| 第 3 级 | 具体修改思路或核验动作 | 可直接复制的完整解法 |

当前仅新版第 2 关 `greeting-v1` 在模型不可用、超时或内容不合格时保留既有基础提示回退；其他题目继续沿用原来的状态处理，不能假定所有题都已有此回退。**分析失败不撤销已有判题结果和提交记录**。

非 `ready` 状态统一 `content=null`、`source=null`；`model` 可以保留实际配置的模型名，通过跳过时则为 `null`。基础提示就绪时 `source=fixed`、`model=null`。新提交在入库时固定映射后的知识点编号，历史读取不按今天的别名重新映射。

本期不定义 `misconception_type`。错题模块可以按 `error_type` 和 `knowledge_ids` 分类，但不能把两者直接当作学生误概念标签。

**9. 提交历史与错题契约**

每次正式提交保存一条独立记录。

历史接口：

```http
GET /api/v1/code/submissions
    ?failed_only=false
    &problem_id=greeting-v1
    &limit=20
    &offset=0
```

`limit` 为 1～50，默认 20；`offset` 默认 0。

记录字段：

```text
SubmissionRecord {
  id: integer,
  problem_id: string,
  schema_version: string | null,
  version: integer | null,
  problem_title: string,
  problem_description: string,
  difficulty: 1 | 2 | 3 | null,
  knowledge_ids: string[],
  code: string,
  judge: JudgeResult,
  analysis: AnalysisResult | null,
  passed: boolean,
  error_type: string | null,
  hints_viewed_max: 0 | 1 | 2 | 3,
  review_source_id: integer | null,
  resolved_later: boolean,
  created_at: string
}
```

这里继续兼容现有命名：

- 提交响应叫 `submission_id`。
- 历史记录叫 `id`。
- 两者指向同一条记录。

题目版本、标题、描述、难度、知识点均保存**提交时快照**。

新提交的版本、难度和知识点来自后端题目定义。迁移前记录没有保存这些元数据时，`schema_version/version/difficulty` 为 `null`，`knowledge_ids=[]`，页面显示“历史记录未提供”；不能读取当前题库来补成当年的信息。旧判题 JSON 没有 `failed_tests` 时由 `cases` 派生，旧错误名读取时规范化。

历史接口 `data` 固定为 `{items, total, limit, offset}`，记录按提交 ID 降序排列。`problem_id` 为精确匹配，`failed_only` 默认为 false。`analysis=null` 表示尚未保存分析或没有历史分析，不表示该次判题失败。含不可公开测试依据的旧分析会隐藏，判题仍可查看。

错题聚合规则：

| 项目 | 规则 |
|---|---|
| 分组依据 | 当前用户 + `problem_id` |
| 进入错题页 | 曾有至少一次失败提交 |
| 后来通过 | 保留错题，显示最近状态 |
| `attempt_count` | 该题版本全部正式提交数 |
| `wrong_count` | 失败提交数 |
| `review_count` | 带有效复习来源的提交数 |
| `latest_passed` | 最新一次提交是否通过 |
| `last_wrong_code` | 最近一次失败代码 |
| `resolved_later` | 某次失败之后是否存在同版本通过记录 |
| 最近复习通过率 | 最近最多 5 次复习计算；不足 3 次返回 `null` |
| 不同题目版本 | 分开统计 |
| 删除失败记录 | 不提供单条学习记录删除接口；账号注销会删除该账号全部提交与复习数据 |

注意：`latest_passed` 与关卡通关状态不同。用户先通过、后提交错误代码，关卡仍保持已通关，但 `latest_passed=false`。

错题列表使用：

```http
GET /api/v1/code/mistakes
```

返回 `data={items,total}`，每项结构如下：

```text
MistakeQuestion {
  problem_id: string,
  schema_version: string | null,
  version: integer | null,
  difficulty: 1 | 2 | 3 | null,
  knowledge_ids: string[],
  title: string,
  description: string,
  source: string,
  first_wrong_submission_id: integer,
  first_wrong_at: string,
  latest_at: string,
  latest_passed: boolean,
  last_wrong_code: string,
  latest_suspected_cause: string | null,
  attempt_count: integer,
  wrong_count: integer,
  review_count: integer,
  recent_review_passed: integer,
  recent_review_total: integer,
  review_rate_percent: integer | null,
  related_questions: []
}
```

版本、难度、知识点、标题和题面取该题最新提交快照，不能取当前题库。`source` 目前为“系统关卡”或“来源待题库提供”。`latest_suspected_cause` 是最近一次可公开且 `ready` 的失败分析中的疑似原因。`related_questions` 固定为 `[]`，没有推荐题时不生成占位题目。

提示查看记录：

```http
PATCH /api/v1/code/submissions/{submission_id}/hints
```

```json
{
  "level": 2
}
```

服务端保存：

```text
hints_viewed_max = max(原值, level)
```

重复请求不重复累计；前端按 1→2→3 展示。只能操作当前用户的失败记录，且该记录必须有可用提示。

返回 `data={submission_id,hints_viewed_max}`。不存在或不属于当前用户为 404；通过记录或分析非 `ready` 为 409；level 超出 1～3 为 422。后端只记录最大级别，不强制请求逐级递增；逐级展示由前端控制。

**10. 课程查询、参考解和通关**

| 接口 | 约定 |
|---|---|
| `GET /code/levels` | 返回关卡发布状态和当前用户进度 |
| `GET /code/progress` | 兼容进度接口，返回所有已通过题目的 `passed_problem_ids`，不保证数组排序 |
| `GET /code/knowledge` | 返回知识点字典的编号、名称和定义，不返回 aliases |
| `GET /code/problems/{problem_id}` | 返回公开教学内容，不返回 tests、hints、参考解 |
| `GET /code/problems/{problem_id}/solution` | 同版本通过后返回参考解与详解 |

以上路径均带 `/api/v1` 前缀。

`/code/levels` 的 `data.items` 为 `{id,problem_id,name,published,status}[]`，其中待开放槽位的 problem_id 可为 null。`/code/knowledge` 的 `data.items` 为 `{knowledge_id,name,description}[]`。

题目详情 `data` 固定包含：`schema_version, problem_id, version, level_no, title, difficulty, knowledge_ids, prerequisite_knowledge_ids, prerequisite_problem_ids, description, story, teaching, starter_code, examples, comparison, time_limit_seconds, output_limit_chars, completed`。

参考解接口 `data` 为 `{problem_id,version,reference_solution,solution_explanation}`。题目不存在返回 404；未通过同版本或题目未发布返回 403。通过状态由已有记录决定，不要求重新通过前置题来证明本关已通过。

关卡状态固定为：

```text
locked
current
completed
```

同时独立返回：

```json
{
  "published": false
}
```

因此：

- `current + published=true`：可以进入。
- `current + published=false`：已解锁、待开放。
- `locked`：前置题未全部通过。
- `completed`：存在至少一次同版本正式提交通过。

未发布关卡不能只靠前端禁用按钮，后端也应拒绝普通学生访问和首次提交。

旧题版本的历史查询与已有错题复习仍应保留。

**11. HTTP、持久化和责任边界**

| HTTP | 含义 | 是否计入学生失败 |
|---|---|---|
| `200` | 判题完成，可能通过也可能失败 | 按 `judge.passed` |
| `401` | 未登录或登录失效 | 否 |
| `403` | 前置未完成、参考解未解锁等 | 否 |
| `404` | 题目、记录不存在或不属于当前用户 | 否 |
| `409` | 当前状态不允许该操作 | 否 |
| `422` | 请求格式或字段不合法 | 否 |
| `503` | 执行器等必要服务不可用 | 否 |
| 其他 `5xx` | 非预期系统错误 | 否 |

保留 FastAPI 的错误形态：

```json
{
  "detail": "请先完成前置关卡"
}
```

422 的 `detail` 可以为数组，客户端不能只按字符串处理。

持久化规则：

- 判题结果成功入库后才认为正式提交已记录。
- 判题先提交入库，再等待分析并补充；查询时可能读到 `analysis=null`，客户端应允许暂时没有分析内容。
- 用户刷新、退出登录不删除提交和进度。
- 本版没有提交幂等键。网络中断后不能盲目自动重发，应先查询历史。
- 同一段代码再次主动提交，会形成新记录。
- 账号注销后不能再访问这些接口；若在判题或分析等待期间注销，保存阶段再次检查账号，返回 401，避免重新产生已删除账号的学习记录。

职责划分：

| 模块 | 负责提供 | 不负责决定 |
|---|---|---|
| 题库与教学内容 | 题目版本、知识点、难度、测试、参考解、基础提示 | 学生是否通过 |
| 后端执行与判题 | 权限、执行、规范错误码、失败测试、脱敏、提交入库、通关状态 | AI 疑似错因措辞 |
| 教学分析 | 有证据支持的疑似原因和三级提示 | 判题结果 |
| 错题模块 | 按账号读取、聚合、展示、记录复习来源与提示使用 | 重新判题、修改历史结果 |

**12. 对接验收、迁移和当前状态**

三方联调至少通过这些场景：

1. 正确代码通过全部测试，保存提交并解锁后续关卡。
2. 写死样例答案时，隐藏测试能识别错误。
3. 语法错误、未定义变量、输入耗尽、超时分别返回规范错误码。
4. `failed_tests` 与 `cases` 的失败项完全一致。
5. 隐藏测试在响应、错题历史和 AI 输入中均不泄露内容。
6. 模型不可用时，判题和学习记录仍正常，基础提示明确标识来源。
7. 重新登录后，通关与提示查看记录仍保留。
8. 用户 A 不能读取或修改用户 B 的提交记录。
9. 错题页重做能够关联原失败提交，并正确统计复习次数。
10. 新题目版本不覆盖旧记录，也不自动继承旧版本通关。
11. 执行器故障不生成学生失败记录。
12. “运行”不生成正式提交，也不改变通关状态。
