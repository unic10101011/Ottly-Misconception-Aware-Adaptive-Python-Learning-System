# 真实 DeepSeek 全流程验收结果

## 一、结论

本轮验收基线为 Git 提交 `ba422fa`，模型为 `deepseek-flash`，验收地址为 `http://127.0.0.1:3000`。

**总体验收结论：部分通过，暂不建议签为完整通过。**

- 程序判题、加练题数据、规则推荐、用户隔离、错题记录、前端构建和主要页面流程通过。
- 真实 DeepSeek 能正常调用，15 个全局错例中 10 个返回有效结果，平均完整耗时约 4.51 秒。
- 5 个错例返回 `invalid_response`，未达到要求中的 15/15。
- 10 个有效结果中，`temperature-max-v1` 的引导把“比较方向写反”解释成“最大值初值问题”，与测试代码的真实错误不一致。
- 内容校验成功拦截了部分无关猜测，但当前拒绝率过高，学生会频繁只能看到“分析未通过检查”。

因此，软件主体流程已经真实可运行，但 AI 分析稳定性和一处分析准确性仍需修复后复验。

## 六、已发现问题与修复优先级

### P0：提高 AI 有效返回率

目标是将 15 个固定真实错例从 10/15 提升到至少 14/15，正式验收要求仍为 15/15。

建议采用最小改动：

1. 给诊断和部分通过引导各增加一次“校验失败后纠正重试”；
2. 重试提示只带上具体拒绝原因和原始公开证据，要求模型删除无依据陈述；
3. 总调用时间继续受现有超时限制；
4. 第二次仍失败时保持 `invalid_response`，不得输出未经校验的内容。

### P0：修复 `temperature-max-v1` 的错误引导

需要让部分通过引导明确比较：学生代码、失败测试输入、实际输出和题目要求，避免把同一知识点内的另一个常见错误当成本次错误。

### P1：修复全量测试隔离

统一在导入应用模块之前设置本轮测试数据库，避免认证测试在全量运行中指向未建表的新 SQLite 文件。

### P1：更新 3 条过时测试

把模型异常时的预期从 `ready/fixed` 更新为：

- `analysis.status=unavailable`；
- 判题结论保持不变；
- 提交记录仍然保存；
- 不生成伪造的误区或固定诊断。

### P2：清理后端旧三级提示兼容字段

当前页面已不展示旧三级提示，但部分 API 响应仍会携带与具体错误不匹配的固定提示。可以保留接口兼容，同时避免这些旧字段被新功能再次误用。
